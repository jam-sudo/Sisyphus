## §1. Problem

The V3 IV-Cmax methodology (commits `4630b0b..4e10ad2`) correctly handles IV bolus by skipping the `t=0` pre-distribution spike via `max(conc[t >= 5 min])`. However, three drugs admitted to the N50 seed (`2907bdf`) are administered as **IV infusion**, not bolus:

| Drug | Infusion duration | Observed Cmax |
|---|---|---|
| Rifampin | 30 min | 17.5 ± 5.0 mg/L |
| Irinotecan | 90 min | 1.66 ± 0.80 mg/L |
| Caspofungin | 60 min | 12.04 mg/L |

The current `pipeline/predict.py` single-dose path deposits `dose_mg` into `venous_blood` as a single instantaneous bolus at `t=0`:

```python
y0 = np.zeros(compiled.n_states)
admin_idx = compiled.state_index[drug.administration_node]
y0[admin_idx] = drug.dose_mg  # all dose at t=0, regardless of route
```

For an infusion drug, the correct physical model is a zero-order input over the infusion duration. Treating the dose as an instantaneous bolus produces a Cmax of approximately `dose / V_venous`, which for rifampin 600 mg gives 162 mg/L — **9× higher than the clinically observed 17.5 mg/L**. This is not an ECM miscalibration; it is a methodological mismatch between the simulated and actual dosing regimen.

Without resolving this, the N50 benchmark cannot produce meaningful predictions for any infusion drug. Since most hospital-administered IV drugs use infusions (not bolus), excluding infusions would gut the N50 substrate pool.

---

## §2. Quantitative Gap (Before/After Motivation)

For IV bolus: `Cmax ≈ dose / V_venous` (at t=0, all dose in venous pool).
For IV infusion at rate `k = dose/t_inf` into a one-compartment with clearance `CL`:

```
Cmax_inf = (k / CL) · (1 − e^(−CL·t_inf/V))
        ≈ (dose / t_inf) · (1/CL) · (1 − e^(−t_inf · ke))
```

For rifampin (dose 600 mg, t_inf 0.5 h, `ke ≈ 0.1 /h`, `V ≈ 70 L`, `CL ≈ 10 L/h`):
- Bolus Cmax: `600 / 3.7 ≈ 162` mg/L (V_venous only, V2 artifact) or `600 / 70 ≈ 8.6` mg/L (full Vss — but engine doesn't compute this at t=0)
- Infusion Cmax: `(600/0.5) · (1/10) · (1 − e^(−0.05)) ≈ 120 · 0.0488 ≈ 5.9` mg/L — order-of-magnitude correct vs observed 17.5

The rough-math "infusion" answer is closer to observed than the bolus answer but still misses (mostly because the simple 1-compartment overlooks sinusoidal hepatic uptake and distribution kinetics). With the proper PBPK engine driving a zero-order input, the infusion prediction should be in the single-fold-error range that matters for generalization testing.

## §3. Existing Infrastructure Audit

The `src/sisyphus/regimen/` module already handles infusion dosing for multi-dose and TDM work:

- `src/sisyphus/regimen/types.py::DosingRegimen.single_iv(dose_mg, duration_h)` — produces a `DosingRegimen` with one event of `duration_h` > 0 encoded as an infusion.
- `src/sisyphus/regimen/solver.py::_expand_infusions()` — splits infusions into `INFUSION_STEP_H`-spaced micro-boluses (for durations above `SHORT_INFUSION_THRESHOLD_H = 0.5 h`).
- The regimen solver iterates the ODE engine segment-by-segment between bolus events, re-using the existing `solve()` path.

**Key observation:** the single-dose `pipeline/predict.py` path does NOT use `regimen/`. It calls `engine.solver.solve()` directly with a bolus `y0`. V3.1 must bridge these.

## §4. Design Alternatives

### Alternative A: Route through `regimen.solver` when `iv_infusion`

Add a branch in `pipeline/predict.py`: when `route == "iv_infusion"` and `infusion_duration_min > 0`, construct a `DosingRegimen.single_iv(dose_mg, duration_h)` and run `regimen.solver.simulate()`. Extract Cmax/Tmax/AUC from the resulting `RegimenResult` concentration-time profile.

**Pros:**
- Re-uses existing, tested infusion machinery (no engine change).
- Zero regression risk for bolus / oral drugs (new branch doesn't touch them).
- Produces physically correct zero-order input semantics (via micro-bolus approximation).
- Infusion-aware `t_min_h` windowing: Cmax extracted from `t >= t_inf` (post-infusion).

**Cons:**
- Two code paths in `pipeline/predict.py` for IV (bolus via engine.solve, infusion via regimen.solver).
- MC uncertainty propagation (`propagate_fast`) is not wired through regimen path — would require extension to get MC PI for infusion drugs.
- The 0.5 h SHORT_INFUSION_THRESHOLD_H means infusions under 30 min are treated as bolus by regimen/solver.py — acceptable (matches clinical convention that short infusions are effectively boluses), but worth documenting.

**Scope:**
- `src/sisyphus/pipeline/predict.py`: add ~15 lines for route branching
- `src/sisyphus/pipeline/predict.py::predict()`: new parameter `infusion_duration_min: float | None = None` (default None preserves V3 behavior for bolus/oral)
- MC path: initial implementation falls back to bolus with `t_min_h = infusion_duration_min / 60 + _IV_CMAX_DELAY_H` (i.e., window after end-of-infusion + 5 min), which is a first-order approximation. Full MC infusion wiring is a follow-up.
- Tests: one unit test per drug class (bolus still works / oral still works / infusion uses regimen path)

### Alternative B: Native infusion in `engine.solver.solve()`

Extend `solve()` to accept `(infusion_rate, infusion_duration)` and add a time-dependent input term to the ODE RHS for the administration node.

**Pros:**
- Single unified code path.
- Full MC support naturally.

**Cons:**
- Engine change — violates the "hard no-touch" invariant on `engine/solver.py` without strong justification (§Invariants #8 in CLAUDE.md).
- The time-dependent RHS requires a conditional term; easy to break the identity-blind property if not careful.
- Duplicates functionality already present in regimen/.

**Verdict:** not recommended. Higher risk, no functional gain over A.

### Alternative C: Static `t_min_h` extension (bolus + windowed max at end-of-infusion)

Keep bolus `y0`, set `t_min_h = infusion_duration_h + _IV_CMAX_DELAY_H`. The engine simulates an instantaneous bolus; the windowed max picks up the post-"infusion" declining concentration.

**Pros:**
- Trivial code change: `t_min_h` formula extension only.
- No route branching.

**Cons:**
- Physically wrong. A bolus at `t=0` does not equal an infusion terminated at `t_inf` — the bolus has distributed further by `t_inf` than an infusion that was still adding drug up to that moment.
- Gives arbitrarily wrong Cmax for long infusions (e.g., 24 h infusion becomes meaningless).
- Would corrupt AUC if AUC is computed over `[0, ∞)`.

**Verdict:** reject. Documented here so future engineers don't propose it again.

## §5. Recommendation

**Alternative A** — route IV infusion through the existing `regimen.solver`. Initial implementation scoped as follows:

### Phase 1 (deterministic, minimum viable V3.1)

1. Add `infusion_duration_min: float | None = None` parameter to `predict()`.
2. Deduce `route_kind`:
   - `"oral"` → oral path (unchanged, `t_min_h=0`)
   - `"iv"` and `infusion_duration_min is None or <= 0.5 min` → IV bolus path (V3 with `t_min_h = _IV_CMAX_DELAY_H`)
   - `"iv"` and `infusion_duration_min > 0.5` → IV infusion path (new)
3. For IV infusion path:
   - Build `regimen = DosingRegimen.single_iv(dose_mg, duration_h=infusion_duration_min/60)`
   - Call `regimen.solver.simulate(regimen, compiled, graph, drug)` (signature TBD — verify existing API)
   - Extract Cmax from the concentration-time profile using windowed max `conc[t >= infusion_duration_h + 5/60]`
4. Deterministic engine prediction (`engine_pk`) uses the regimen path.
5. MC (`propagate_fast`) initially continues to use the bolus path with a warning flag; MC-for-infusion is Phase 2.

### Phase 2 (MC integration, deferred)

Wire `propagate_fast` or a new `propagate_regimen` to run the infusion simulation under MC parameter realizations. This requires extending the scipy-backend loop to call regimen.solver per sample. Out of V3.1 scope; deferred to a dedicated design.

### Phase 3 (API cleanup, deferred)

Consider retiring the `route == "iv"` string-based branching in favor of a `Route` enum or a structured `DosingRegimen` first-class input to `predict()`. Would reduce the conditional logic to routing-by-type. Deferred.

## §6. Contract and Invariants

- **Backward compatibility:** `predict(smiles, dose_mg, route="oral")` and `predict(smiles, dose_mg, route="iv")` (no `infusion_duration_min`) behave exactly as in V3. The 107-holdout and the currently-committed 4track predictions file are byte-identical after this change.
- **Engine identity-blind invariant preserved:** no string matching on drug names, no per-drug branches. `regimen.solver` already respects this.
- **Hard no-touch list preserved:** no changes to `engine/compiler.py`, `engine/solver.py`, or `DrugOnGraph` fields.
- **Distribution-native invariant:** infusion rate is deterministic (dose/t_inf); uncertainty enters via parameter sampling per usual.
- **Compile once, parameterize many:** regimen.solver already compiles once per drug and runs segment-by-segment; invariant preserved.

## §7. Test Plan (for Phase 1 implementation)

1. **Unit: route dispatch.** Verify `predict(route="oral")` does not touch regimen.solver; `predict(route="iv", infusion_duration_min=None)` uses engine.solver bolus; `predict(route="iv", infusion_duration_min=30)` uses regimen.solver.
2. **Regression: bolus unchanged.** For a known IV bolus drug (e.g., valsartan from ECM generalization), `predict(route="iv")` Cmax must equal the V3 benchmark value to 1e-6 relative error.
3. **Regression: oral unchanged.** Re-run the 107-holdout and verify Meta AAFE 2.695 is preserved exactly.
4. **New: infusion sanity.** For rifampin 600 mg 30 min, the engine Cmax must be less than the bolus-equivalent `dose / V_venous = 162` mg/L. (Not yet verified against observed 17.5 due to engine calibration unknowns; sanity check only.)
5. **New: short infusion = bolus fallback.** `predict(route="iv", infusion_duration_min=10)` (short, < 30 min threshold) falls back to bolus path. Documented behavior.

## §8. N50 Benchmark Gate

V3.1 Phase 1 is a **prerequisite** for the N50 benchmark run because 3 of the 3 current seed drugs are infusions. Until V3.1 Phase 1 lands, the N50 benchmark script does not exist and is not runnable.

Upon V3.1 Phase 1 landing:
- A new benchmark script `scripts/run_n50_benchmark.py` iterates N50 entries, reads `infusion_duration_min` per drug, and routes to the appropriate predict() path.
- The benchmark is run **once** per the N50 spec §7 freeze rule.
- Results (N50 AAFE ± 95% CI) are published in CLAUDE.md headline.
